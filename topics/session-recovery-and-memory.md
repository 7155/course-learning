# 请求恢复：超时后怎样避免重复执行

整理于 2026-09-19。来源：PAW 学习仓库第 34 课，配合第 64 课。原课描述 2026-09-08 的源码快照；这里提炼机制，不宣称当前安装版本已验证。[来源说明](../sources/local-learning-site.md)。

## 超时到底意味着什么

一次用户提交可能已被 Runtime 接受，但响应或本地投影失败。客户端超时只证明没收到确定答复，既不证明“没有执行”，也不证明“任务成功”。因此恢复应查找原请求的接受证据，而不是立刻再发送一次。

原课的窄入口是 `AgentPromptApplicationService._recover_accepted_prompt`。它查证据并恢复原 turn 的接受响应，不调用模型、不重新投递 prompt。这是职责边界，不是用摘要猜状态。

## 一个状态例子

教学请求 `msg-demo` 已登记为 pending，绑定输入摘要。Runtime 已返回原 turn 身份，本地保存了接受证据，但后续投影失败。

```text
同一请求身份 → 查询本地接受证据
            → 没有时查询匹配的持久事件
            → 核对请求内容与重试关系
            → 事务内复验当前状态
            → 返回原 turn 的 accepted；投影仍可标为 partial
```

有证据才改变 pending；没有证据就保持未决。同 ID 换了输入不能借旧回执通过。两个恢复者都看到 pending 时，最终写入仍需在事务内复验，不能各自创造结果。

原课还强调查证据的优先级：拿到本地证据却发现身份不匹配，不应继续挑另一份更有利的证据来“凑成功”。

## 它保证到哪里

accepted 表示请求被接受，不等于工具已经完成，更不等于用户目标通过验收。partial 表示可恢复原执行身份，但显示投影未必已追平。数据库事务保护本地记录，不能让 HTTP 回包和外部副作用自动加入同一个原子事务。

与 [Pi Session/Compaction](../notes/2026-09-11-pi-agent-runtime-deep-dive.md)连接：历史摘要保留工作上下文；持久回执与事件支撑执行事实。两者不能互相替代。与 [Sandbox](../notes/2026-09-13-agent-sandbox-runtime.md)连接：文件恢复后仍需确认进程和外部操作状态。

## 验证方法

在发出前、Runtime 接受后、本地保存证据后、返回客户端前分别制造失败，重试时沿用相同请求身份。检查真实派发次数、turn 身份、冲突拒绝和未决状态。只是 UI 只显示一条消息，不足以证明后端没有执行两次。本次没有进行产品级故障注入。

费曼问题：两个恢复者同时找到接受证据，为什么最后还要在事务里重读状态？

<details><summary>参考答案</summary>

找到证据时读到的只是当时快照，另一条路径可能已收口。事务内复验让竞争者重放同一原结果，而不是覆盖或创建新结果；它仍不证明远端副作用实现了 exactly-once。

</details>
