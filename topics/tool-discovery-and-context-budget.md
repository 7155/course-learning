# 工具 Schema 渐进披露：看见能力与执行能力

整理于 2026-09-19。来源：PAW 私有学习仓库第 33 课。本文是概念提炼，原课的源码观察日期为 2026-09-08，不是当前产品验收；[来源清单](../sources/local-learning-site.md)。

## 要解决的问题

工具多时，完整参数 Schema 长期进入上下文会挤占预算。只给名字又容易让模型猜错参数。渐进披露的学习主线是：先搜索短卡片，再按下一步需要加载精确工具的完整 Schema，最后调用真实工具。

原课以 `createDiscoveryToolsExtension`、`BackendToolRegistry` 和 `applyBackendToolDisclosure` 为历史源码锚点；执行检查归 `ControlToolGateway`。这里保留职责关系，不复制私有源码或声称当前实现未变化。

## 具体例子

教学 Session 的授权目录包含 overview、memory、knowledge，起初只有 overview 自动可见。模型先搜索能力，再加载 memory 和 knowledge。加载层应先检查整批名字是否合法、可发现、是否重复，再更新可见集合；加载成功并不执行查询或修改记忆。

```text
授权目录 → 搜索短卡片 → 校验本批目标 → 必要的加载回执
        → 披露 Schema → 下一轮模型调用 → 执行时再次校验
```

原课将模型用的短结果与恢复用的完整 details 分开：这样既不重复把大段 Schema 塞进工具结果正文，又保留 Session 重开所需的加载身份。恢复只采用当前分支里成功加载的机器结果，并重新检查当前目录。模型一句“我加载过”不能恢复能力。

## 失败与取舍

如果第二个工具不存在，边加载边校验会留下“返回错误但第一项已生效”的半批状态。先校验后披露可避免这种本地失败；涉及远端回执时仍不自动获得跨进程原子事务。

若旧目录已删除工具，重开 Session 不能照历史直接恢复它。若工具仍可见但 Session 已改为只读，真正写操作仍要在 Gateway 拒绝。Schema 的可见性不代替授权。

与 [Code Mode](../notes/2026-09-11-browser-control-and-code-mode.md)连接：前者优化能力说明，后者优化确定性控制流；两者都应保留原工具执行边界。减少 Schema 字符数不等于降低总费用，发现与加载也消耗模型轮次。

## 怎样检查是否真的更好

固定模型、任务、工具目录、工具结果和验收标准，比较全预载、逐项加载和小批加载。先检查任务成功、错误工具名、参数拒绝和遗漏能力，再比较加载次数、总 tokens、费用与延迟。本次未运行该实验。

费曼问题：重开 Session 时，历史上成功加载过的工具为何仍可能不可用？

<details><summary>参考答案</summary>

成功记录证明过去发生过加载，但当前目录和权限可能变化。恢复必须重新核验目录资格，实际调用仍经过执行层。否则旧历史就成了绕过当前能力限制的入口。
