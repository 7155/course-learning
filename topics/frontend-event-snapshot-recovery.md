# 前后端同步：事件流、快照与迟到响应

整理于 2026-09-19。来源：PAW 学习仓库第 64 课，历史源码观察日期为 2026-09-08。本文只提炼恢复思路，[来源说明](../sources/local-learning-site.md)。

## 页面怎样可靠地观察任务

事件流提供增量，快照用于重建当前投影。事件到达、页面显示、Runtime 完成是不同边界。原课把职责拆给 EventHub、SSE transport、live owner 和 reducer；组件显示状态不能反过来成为任务完成的依据。

## 一次断线的例子

页面已应用 sequence=8，第 9 条未完整交付，重连却收到第 10 条。若直接拼接，会掩盖缺失的信息。恢复流程应识别缺口、暂停普通增量、获取快照、从合法游标继续；重复事件则按身份去重。

```text
连续事件 → 更新投影
重复事件 → 忽略
发现缺口 → 请求快照 → 校验快照资格 → 重建 → 恢复订阅
```

SSE 的传输分块不等于事件边界；原课的 parser 以完整帧交付后才推进游标，未完成帧不能因为其中一段 JSON 看似完整就被提交。

## 快照晚到为什么仍可能旧

请求发起时间、服务端采样时间和响应到达时间不同。页面已经收到终态后，旧请求的 busy 快照才到，若“最后响应获胜”就会把完成任务重新显示为运行。

原课使用 sequence、请求 generation 和终态语义共同约束合并。sequence 也不是唯一条件：同游标快照可能用于修复观察状态；恢复控制事件不能被误当成新的正式业务进度。具体合并规则必须按协议定义验证，不能简单地一律拒绝同序号快照。

请求接纳中，本地乐观消息需要与后端精确 clientMessageId 关联。一个采样较早的 idle 快照不能证明刚提交的消息失败。刷新观察和重新执行业务是两个动作。

## 验证与取舍

可固定一段事件脚本，注入半帧断线、重复事件、缺口、晚到快照和关闭订阅，检查正文不丢、终态不回退、缺口能恢复、资源能释放。解析单测不等于 Electron 真实网络栈验收。本次未运行这些产品检查。

短暂的一次性结果可以返回完整 JSON；长任务、多窗口和刷新恢复才会增加事件与快照协议的价值和复杂度。

费曼问题：关闭观察流是否应该直接停止 Agent？

<details><summary>参考答案</summary>

不应混淆。释放订阅解决连接与观察资源，停止 Agent 是独立业务命令。否则关窗口或断网就会意外改变任务生命周期。
